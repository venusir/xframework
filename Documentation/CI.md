## 二、成本要点（三条指定内容）

### 2.1 Unity 许可形态（跑 Unity batchmode 的前置）

- 三条门禁里**测试门禁必须启动 Unity**（batchmode，`Tools/run-tests.ps1`）；编译/文档门禁走 `dotnet build`，
  而 **csproj 由 Unity 生成、不入库**（`.gitignore` 排除 `*.csproj`，`Workflow.md` §六 记了这条依赖）——
  干净克隆上必须先有一次 Unity 导入，两条 `dotnet` 门禁才跑得起来。
- 托管 runner 上的许可：Personal 许可证可用，但要 **`.ulf` 许可文件 + 账号凭据**存进 CI secrets，且
  **Personal 许可会过期、需定期重激活**（社区已有专门的自动刷新动作）`[网上读取]`；Pro / 企业另有序列号
  或 Build Server 浮动许可（独立产品、额外成本）。**这条维护链是「做」的主要代价。**
- `ProjectSettings/ProjectVersion.txt` 钉 `6000.4.5f1`：托管 runner 每次现装该版本（补丁版可得性 `[未核对]`）。

### 2.2 runner 形态

- 游戏类 CI 镜像（game-ci 等）**以 Linux 为主**；Windows 容器镜像存在，但主要面向 IL2CPP 且有限制
  （VS 构建工具许可、容器许可每次构建要领还）`[网上读取]`。社区在 GitHub Actions 上的 Windows 路线多为
  「windows runner + Hub 现装 Unity + 非 Docker 动作」`[网上读取]`。
- 本仓门禁脚本是 **Windows 形态**：PowerShell + 测试壳用 junction（`run-tests.ps1` 头部）——Linux runner 上
  测试壳机制直接不可用，只能 `-UseRepo`。
- **公开仓 + 自托管 runner 被排除**（见 §一）：fork PR 的代码会在自托管机器上执行，GitHub 对此有明确警告。

### 2.3 与测试壳的关系

- 测试壳（`<仓库名>.TestRun`，junction 共享 Assets/Packages/ProjectSettings、独立 `Library`）解决的是
  **本地**问题：不关编辑器也能跑 + Unity 生成的 `.meta` 回写真实仓库。**CI 上这两个前提都不存在**
  （无打开的编辑器、无回写需求）——托管 runner 上改用 `-UseRepo`（脚本自带该开关）即可。
- **冷导入成本**：干净 runner 上 Unity 首次导入工程会生成完整 `Library`（分钟级），每次运行都要付
  （可缓存，但随 Unity 版本漂移易碎）；本机跑因为有常驻 `Library`，感受不到这笔。
- 门禁耗时（本仓实测）：测试约 82 秒（双平台）+ 文档约 90~180 秒，另加 Unity 启动与导入。

### 2.4 CI 能覆盖与不能覆盖的

- **能**：三条机械门禁在 push / PR 上自动跑，「阶段收尾记得跑」不再依赖人脑。
- **不能**（与 `Workflow.md` §六 同）：关闭域重载手工验收、文档分层、`.md` 语义、偶发用例的「重跑一次再判」、
  以及公开 API 基线反写后的「看一眼差异」——这些本来就没有机械替代。

## 三、若重开（「做」时的最小路径）

方向（**不是施工单**，实施另起一轮 Plan Mode）：仓库级 workflow → checkout → 先跑一次 Unity 导入（顺带生成
csproj）→ `pwsh -File Tools/run-tests.ps1 -UseRepo` → `pwsh -File Tools/check-docs.ps1 -Enforce`；许可走
`UNITY_LICENSE` / 凭据 secrets，重激活用社区动作或手工轮换。

## 四、重开判据（可判定）

任一条成立时重开本条目：

1. **出现第二个贡献者或外部 PR 流程**（人脑门禁的失效模式自此才有第二个触发者）；
2. **发布节奏显著加快**（如单周多次发布）**且实际发生过一次漏跑门禁**；
3. 仓库转私有（自托管 runner 的安全边界随之解除，成本更低的那条路重新可用）。
