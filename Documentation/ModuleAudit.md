# XFramework 模块审计手册

> 本文是**开发者向**的审计判据：对某个模块做「找潜在问题 + 第三方对照 + 改进建议」这类审计时，**该看什么、拿什么命令看、每条看不到什么**。
> 规则在 `CLAUDE.md`、流程与门禁在 `Documentation/Workflow.md`，本文不重复它们，只在判据处引用。
> 快照日期：2026-09-27。

## 一、这份手册解决什么

一次模块审计的固有成本分两半：**读代码、跑验证、查对标实现**——这些该花；**「该找哪些类的缺陷」**——这一半每次都在重新推导，不该重复花。

判据从哪来：对全仓 `CHANGELOG.md` 的 `### Fixed` 段做一次归纳，每条缺陷都自述了根因与「为何此前没被测出来」。因此下表里的每一类**都不是通用最佳实践的移植，而是本仓真实流过的血**——按出现条目量看，**「文档/注释与实现相反」是数量最多的一类**（具体条数不写进本文：它是会随开发增长的量，抄进来必然过期，见 `CLAUDE.md` 的「不写固定例数」）。

## 二、一次审计的四步

```
① 普查  →  ② 判据逐类扫  →  ③ 定向验证  →  ④ 报告与拆分
```

1. **普查**：模块的文件清单、公开面、依赖方向、消费方（谁在用这个模块的什么）、测试覆盖到哪。子代理并行做这一步很划算——它不需要判断力，只需要全。
2. **判据逐类扫**：按下面第三节的清单逐类问。**不必逐类都命中**，但每类都要留下「扫过了、无问题」的痕迹，否则报告无法区分「没找到」与「没看」。
3. **定向验证**：可疑点必须落到证据上——**只有编译器知道答案的问题就写复现程序编译**（重载决议、二义、cast 行为），**只有第三方知道答案的问题就读它的源码**（例如 UniTask 的 `Forget()` 到底把异常交给谁），**只有仓库知道答案的问题就跑门禁**。此步的纪律见 `Workflow.md` §三。
4. **报告与拆分**：见第五、六节。

## 三、缺陷类清单

每类四问：**判据**（怎么问）、**本仓实例**（真发生过什么）、**探针**（拿什么命令看）、**抓不到什么**（这一条的边界——仓内最好的范式是 UI README「扩展清单」那句「它拦不住的是转发接错线与假转发，那两条只能靠行为测试」）。

### A. 契约与文档

#### A1 文档/注释与实现相反

- **判据**：README/XML 承诺的行为，回源码**逐条**核；反过来，公开成员有哪些**文档里一字未提**。
- **本仓实例**：Settings `Reset`/`Load` 忽略 `defaultFactory`（「文档与实现相反」）；UI README 的约定式绑定章节描述的是一套**不存在的机制**；Update README 里有一段**无法编译**的示例；Settings README 记录过**一整套代码里不存在的 API**；Message 承诺过的「销毁令牌订阅绑定」**那段代码从未存在**。
- **探针**：`grep -nE "^\| |^- |^> " <模块>/README.md` 列承诺 → 逐条回源码核；反向用反射列出公开成员，再 grep 文档看谁没被提过。
  **修一处时先找齐所有落点**（2026-10-01 新增，Update 二轮）：同一句错话常同时活在 README、XML 注释与行内注释里，只改被引用的那一处，其余落点会继续教错人——用那句话里的关键词（成员名、枚举名、断言里的名词）全仓 grep 同义句，一处一批改完。实例：Update 的 `Enable` 档位口径，2026-09-30 那轮判定「代码对、文档错」并只改了 README 两处，`UpdateScheduler.cs` 里三处 XML / 行内注释仍写着相反的行为，到 2026-10-01 第二轮才补齐——**而第二轮正是用这条规则自查时，又抓出第四处**（`PendingOpKind.Enable` 的枚举注释），可见「找齐」一次也未必够。
- **抓不到什么**：机器只能查「成员是否存在」，查不了**语义是否相反**——后者必须逐条读。

#### A2 契约面缺口（实现了但够不到 / 承诺了但没做到）

- **判据**：接口声明的成员，门面有没有**同名转发**？（没有 = 第三方根本调不到）；接口承诺的**边界行为**（不抛、返回 false、未初始化返回空），实现有没有反例？
- **本仓实例**：UI `SetLayerVisibility` 曾「方法完整、文档也有，但只在内部实现上」；`SettingRef.TryWriteValue` 违背 `IReactivePropertyWriter<T>` 唯一承诺（失效时该返回 `false` 不抛，实际抛）；UI 门面探测型查询在未初始化时抛异常（文档说返回空值）。
- **探针**：反射比对（先例 `Tests/Runtime/UI/UIFacadeCompletenessTests`、`Tests/Runtime/Settings/SettingsFacadeCompletenessTests`）；再人工做一张「接口承诺 × 实现行为」对照表。
- **抓不到什么**：转发**接错线**（A 转发到了 B）与**假转发**（空实现、抛异常）反射看不出来——那两条只能靠行为测试。

#### A3 XML 未转义 → 整块注释被丢弃、cref 死链隐形

- **判据**：注释里出现未转义的尖括号/`&` 了吗？`<see cref>` 指向的成员**真的存在**吗？
- **本仓实例**：XPool 模块一处 `<c>Get&lt;T&gt;()</c>` 式的未转义触发 CS1570，**整块注释被编译器丢弃**，块内 `cref` 随之不再被检查——死链表现为「**没有**告警」而不是「有告警」。
- **探针**：`pwsh -File Tools/check-docs.ps1 -Module <模块名>`（诊断）；`-Enforce` 是门禁。注意它必须**全量重编**，增量不下发警告。**它的统计范围只有 CS1570 / CS1574**——CS0419（cref 二义）、CS1591（公开成员缺注释）等同样由这条通道产出却不被统计（见 §八），判「cref 都有效」之前先确认这一点（实例：Update 二轮实测发现包内有 CS0419 存量，而 `-Enforce` 照常判绿）。
- **抓不到什么**：注释内容与实现不符（编译器只管 XML 合不合法）。

### B. 生命周期与并发

#### B1 单向闩锁 / 释放后仍可用

- **判据**：`Destroy`/`Dispose`/`Shutdown` 之后，**逐个公开成员**问：此刻调用会怎样？抛的异常消息里教用户做的事，照做能成功吗？
- **本仓实例**：Settings `Destroy` 后永久不可用（单向闩锁，而异常消息写着「请重新调用 Initialize」——照着做会再抛一次）；`Dispose` 只终止通知流、未置释放标志，于是仍可写盘；`ReactiveProperty.Value` 的 getter 对「已释放」曾有两种态度。
- **探针**：把生命周期终点当作状态，逐个成员列表核对（先 `grep -n "public "` 列成员）。
- **抓不到什么**：并发进入同一状态的时序问题。

#### B2 回池 / 销毁后仍被回调

- **判据**：每处「发布↔订阅」与「回池/销毁」的配对处问：**退订挂在哪一步？回池走不走那一步？**只销毁不销毁的路径（回池）最容易漏。
- **本仓实例**：UI 面板回池不解绑 ViewModel、`UIBinder.BindToLocalizedText` 的订阅无人释放、Tip 在 `CloseAllAsync` 后永久失效、HUD 先 `.Forget()` 再回收导致关闭续体跑在**已回池的实例**上。
- **探针**：`grep -n "OnDestroy\|OnPoolRecycle\|Dispose\|Track("` 找释放点，再核对每条回收路径。
- **抓不到什么**：只有真实回收路径才暴露；替身对象常结构性绕开（见 D3）。

#### B3 异常隔离不对称

- **判据**：**同一类失败**在不同路径上的处置一致吗？列出全部路径，空单元格就是缺陷。
- **本仓实例**：File 的「可选能力缺失」未加密时告警降级、加密后**抛** `NotSupportedException`（另一处更隐蔽：启用加密后**静默**返回空数组）；Message 的 fire-and-forget 与 await 两条路径日志不同形（一条落到 UniTaskScheduler、无模块前缀）；订阅回调异常被吞、注册期立即回调异常却上抛。
- **探针**：对每个 `catch`、每个「失败返回」，找同类失败的所有路径做对照表。
- **抓不到什么**：**路径枚举的完整性**——漏掉的路径就是漏掉的缺陷。

#### B4 线程契约只在散文里

- **判据**：README/注释里声明的线程契约，代码里有没有**执行它的东西**（断言、守卫、切回主线程）？
- **本仓实例**：Message 引擎的锁曾被读成「允许跨线程发布/订阅」的许可（实际只是容忍并发退订）；Save 的「全程不切回主线程」契约下，域根解析却落在子线程；正面例子是 Pipeline 阶段写入的主线程断言与 Message 发布/订阅入口的断言（Editor 断言 + 只报首错）。
- **探针**：`grep -rn "线程\|Thread" --include=*.md <模块>/` 找契约声明 → 回代码看断言是否存在。
- **抓不到什么**：断言覆盖不到的路径（例如令牌取消回调可能在任意线程执行）。

#### B5 该回收的没回收 / 无界增长与陈旧重放

- **判据**：对每个「以键/实体/类型为单位创建」的容器问：**谁负责淘汰、在哪个调用点、漏了会怎样**——是内存不回落，还是更糟的**陈旧值重放**？
- **本仓实例**：Message 缓冲通道曾只有新增没有淘汰（内存无界）；无值缓冲通道永远不可回收（连兜底 API 也摘不掉）；淘汰后残留「已可回收但仍在表中」的空壳；`BufferedEventStream` 曾因方法隐藏导致**经接口释放不清缓存**，已释放的流仍向新订阅者重放陈旧值。
- **探针**：找 `Dictionary` 字段 + 问「增删配对在哪」；对键基数高的场景特别警惕（实体 Id）。
- **抓不到什么**：键基数低时不显形，要构造高频键才暴露。

#### B6 共享协调协议代际覆盖面（2026-10-01 新增，Asset 一轮）

- **判据**：协议里凡「由当前一代写入、由**任意一代**读取」的共享槽（等待者表、异常槽、任务槽）都是代际漏洞的
  候选。把该槽的**每个读写点**标上代际，逐点问：**旧一代能否写到新一代头上？** 再加一问：`Destroy`/`Dispose`/
  `Shutdown` **清了哪几个槽、漏了哪几个**？
- **本仓实例**：Asset 门面的 `_initWaiters`（全局列表）与 `_initException`（全局异常槽）未按代际分区——
  `Destroy()`/`SetInstance()` 递增代际号并清 `_initializeTask`，却把这两个槽原封不动留下；于是「作废后重新
  初始化」时新旧两个创建者并存，**旧代际收尾放行了新代际的加入者**（它们醒来时 `IsInitialized` 仍为 false），
  或把旧代际的异常广播给它（实测复现，5 条用例红）。前一轮修「共享任务 + 代际号」时只覆盖了**任务槽**一个。
- **探针**：`grep -nE "static .*(List<|Dictionary<|Exception|UniTask)" <模块>/*.cs` 列出全部静态共享槽 →
  对每个问「它的读/写有代际过滤吗」；再逐个生命周期终点问「它清了哪些槽」。
- **抓不到什么**：只有一个代际（没有作废/重建路径）时完全无害——只在「作废 + 重新进入」这条路径上显形，
  且**冒烟用例照常绿**。

### C. 绩效与平台

#### C1 每帧路径的分配与反射

- **判据**：这段代码**多久被调一次**？——**频度是判据的前提**：同一段代码在初始化路径上无所谓，在每帧路径上就是缺陷。分配源清单（LINQ、闭包、拼接、组件查找、装箱…）见 `CLAUDE.md` 的「性能与 GC 约定」，本文不重复。
- **本仓实例**：仓内既有对策的样板是 `DispatchListPool`（每帧派发路径刻意不走 PoolManager 的字典查找）与各处 `readonly struct` 句柄；反例是 UI Tip 曾自建帧通路（既不受 `UpdateManager.Pause` 约束、也不进 LOD 调度）。
- **探针**：`grep -nE "\.(Where|Select|OrderBy|ToList|ToArray)\(|GetComponent|Camera\.main|FindObjectByType|new List<|new Dictionary<|\\\$\"" <文件>`。
  **这条探针的实测画像**（两次实跑得出，别当它是精确的）：第一版写 `new `，把 `new ArgumentNullException` 这类错误路径分配全捞进来；收窄后又会把**字段初始化器**（`private readonly List<T> _x = new List<T>(8);`）捞进来——那些是一次性分配。所以它的定位是**把范围缩到几十行**，判定完全靠人工问频度（谁调它、每帧还是每次操作）。
- **抓不到什么**：分配量小但频次高；或分配发生在**库内部**（要读第三方源码）。

#### C2 平台/引擎隐式行为（静默截断、帧率相关基准）

- **判据**：任何「把两个数算在一起再交给引擎」的地方问：引擎那侧的**取值范围与单位**是什么？查官方文档 + **实测一次**。
- **本仓实例**：`Canvas.sortingOrder` 运行时只保留 **16 位有符号**（实测 `100001 → -31071`），既有的 `layer × 1000` 方案在层号 ≥ 33 时全盘失效；UI 遮罩层级不钳制，传 2000 算出 64031 回绕成负值跑到所有面板后面；Update 档位曾按**帧数**计节拍（30fps vs 144fps 差 4.8 倍）；面板用 `Time.deltaTime` 积分在低频档位下慢 8 倍。
- **探针**：对每个「跨边界传值」点写一行实测（打印回读值），不要靠推理。
- **抓不到什么**：只在真机/特定平台出现的差异。

### D. 边界、纪律与测试

#### D1 跨模块引用 Internal / 依赖方向

- **判据**：生产代码引用了别的模块的 `Internal` 命名空间吗？两个公开模块之间的依赖方向**说清了吗**（README 的依赖节）？
- **本仓实例**：曾经 5 个跨模块文件引用 `XMessage.Internal`（已由 `XFramework.XEvent` 模块解决）；UI 为十行适配器内联过本地副本（正确做法）。
- **探针**：`Tests/Editor/Architecture/ModuleBoundaryTests`（两条断言：源码扫描 + 公开面反射扫描）。规则见 `CLAUDE.md`「模块边界」。
- **抓不到什么**：公开 API 之间的**语义耦合**（只能靠人看依赖方向是否合理）。

#### D2 重载决议与二义

- **判据**：新增/修改重载后，**既有调用形状**的解析会不会变？有没有形状会被两个重载同时接住？
- **本仓实例**：`PublishAsync(x, y)` 两参二义（键值重载因此取消 `strategy` 默认值）；`SubscribeBuffered` 键值带过滤扩展重载（加之前先写复现程序验证）；`Register` 报错提示里 `TResponse` 是**字面量**（照抄得到的代码编译不过）。
- **探针**：**写独立复现程序编译验证**——本仓纪律：涉及重载决议不靠纸面推理；**并配一个负向控制**（造一个本应报错的形状，证明验证程序真有判别力）。
- **抓不到什么**：运行期才现的二义（罕见）。

#### D3 测试的假绿与适用边界

- **判据**：这个 fixture 注入的替身**绕开了什么**？这条断言**在修复前会不会红**？哪些公开成员**零直接覆盖**？
- **本仓实例**：8 个 File/Save fixture 全注入 `TempFileProvider`，**结构性绕开 Unity API**，于是「域根解析碰了 Unity API」这整类缺陷在替身上不可见——唯一用真实 Provider 的用例红了 7 次、失败消息逐字相同，**被当成了环境噪音**；Settings 有条用例**生来就错**（与同文件另一条断言直接矛盾）；有条注释与实现相反却**靠相对断言侥幸通过**；UI 排序空间**曾经没有任何用例断言过** `sortingOrder`；并发缺陷的**冒烟用例绿色不构成证据**。
- **探针**：对每条断言问「改前会不会红」（`Workflow.md` §三.1 的反面用法）；用反射列公开成员 → grep 测试目录找零覆盖；`grep -rn "TempFileProvider\|Fake\|Stub\|Mock"` 看替身绕开了什么。
  **「零覆盖」这条探针的实测画像**（Save 试跑得出）：按名字 grep 会把**同名跨模块**（`CurrentVersion` / `Message` / `Initialize`…）与**经 lambda / `var` 使用**误判成「有覆盖」——实测 24 个公开成员里真缺口只有 1 个。命中不等于有断言，逐个复核是这条探针的固定成本。
- **抓不到什么**：无法证伪「没有测试」，只能列出缺口。

#### D4 静默失败

- **判据**：失败时调用方**能不能知道**？知道了能不能**区分原因**？「有意宽容」有没有写进文档？
- **本仓实例**：Message 全局过滤器曾拦截不生效且无提示；Save `ApplySnapshot` 曾跳过恢复失败的块却照常回报成功；Settings 读文件失败静默回退默认值（有意，但必须能在文档里找到依据）；Save 的「主文件与备份都不可用」曾只回报主文件原因，分不清「没有备份」与「备份也坏了」。
- **探针**：逐个 `catch`、`return false`、`TryXxx` 问上面两句；对照 README 有没有承诺「失败会被报告」。
- **抓不到什么**：「有意宽容」与「意外吞掉」在代码上长得一样，要靠注释与 README 的承诺来区分。

#### D5 跨模块能力缺口

- **判据**：这条实现**被迫与自己的文档理由相悖**吗？没做到时再问一次：**是本模块偷懒，还是它拿不到需要的原语**？——后者就是这一类，症状像 A1/D4，但**改法不在本模块**。
- **本仓实例**：Save 的 `ISaveManager` 自述「所有涉及 IO 的成员一律异步——同步 IO 会阻塞主线程，而 Console 等平台的 Provider 可能是数百毫秒的 SDK 调用」，但内部删除路径调的是 `FileManager.Delete`（**File 模块只有同步删除原语**），于是删除/移动在主线程做 1~4×N 次同步删除。Save 侧写法没错，修法在 File 补 `DeleteAsync`（跨模块 API 变更）。**反证同模块**：恢复扫描刻意不切回主线程、删除落在池线程，故不受影响——同一模块里两种删除路径的对照正是判据的落点。
- **探针**：`grep -n "异步\|阻塞\|主线程\|必须\|一律" <模块>/*.cs <模块>/README.md` 找出**理由句**（注释里解释「为什么这么做」的句子），逐条问：代码做到了它说的吗？
- **抓不到什么**：跨模块的修法要另一个模块的计划。本类只负责**如实记进 README 的「已知限制」并立待立项**——审计不替它开工。

### E. 键空间与相等语义（2026-09-28 新增，Lock 一轮）

- **判据**：模块用裸值类型（`int` / `string` 等**值相等**类型）作全局注册表的键吗？两个**互不相关的作者**取到同一个值时——编译期有提示吗？运行期是合并、覆盖还是报错？「键相等」被文档定义为「同一个持有者」了吗？
- **本仓实例**：Lock 的 `lockType`（裸 `int`，README 还建议各模块自建同名静态类）与 `lockObj`（存 `HashSet<object>`，值相等）——两个来源取同一个名字即静默合并，一方释放连带清掉另一方的锁（实测 `GetLockCount` 为 1 而非 2、另一方 `IsHeld` 变 false）。同轮的另一半是**主体键**：默认比较器按 `Equals` 判等，实体按 Id 重写 `Equals` 时两个不同实体共用一个键（实测：给 A 加锁 B 也被锁、计数合并）。对照：Unreal GAS 的 tag 容器按**计数**维护同名 tag（多来源各自计数，移除只减自己那一份）。
- **探针**：`grep -nE "Dictionary<|HashSet<"` 列出所有键 → 对每个键问「另一个模块/另一个作者取同一个值会怎样」；`grep -n "const int\|static class .*Type"` 找「命名空间靠文档约定」的键域；对**引用类型键**追加一问：比较器是默认的吗（那就会走 `Equals` 重写）？
- **抓不到什么**：单模块内看不出来——只在**两个独立作者**（或两个值相等的实例）相遇时显形，单测天然写不出来（要么构造两个替身，要么靠人推演）。

### F. 双观测面语义不一致（2026-09-28 新增，Lock 一轮）

- **判据**：同一件事有「事件」与「查询」两个观测面时，两者的**粒度**一样吗？事件是「集合边沿」还是「聚合状态翻转」？订阅者照事件维护一份状态镜像，会和查询面一致吗？
- **本仓实例**：Lock 的 `OnLocked`/`OnUnlocked` 是每个 (主体,类型) 集合的**边沿**，而 `IsLocked`/`GetLockCount` 是含全局锁的**聚合**——全局锁释放时，仍被自己的锁挡住的主体照样收到 `OnUnlocked`（实测），订阅者照事件维护「现在能不能动」即显示错状态。同族：`OnGlobalLocked` 名字里的 “Global” 指框架级事件总线，而实现是「任意主体的首次锁」——名字与语义各说各话。
- **探针**：列出公开事件面 → 逐条与查询面对照，问「事件触发时查询面一定翻转了吗？反过来呢？」；再拿订阅者的典型用法（「照这个事件维护镜像」）走一遍。
- **抓不到什么**：两个面各自自洽时无法判定谁对——只有把订阅者的**典型用法**写出来才看得见偏差。

## 四、报告格式

1. **按严重度排序**，每条给**理由**（为什么这是问题、代价是什么）；不分严重度平铺 = 让读者自己排优先级。
2. **「不该做」也写成结论**——评估后决定不动的项要写明理由，否则下一轮审计会把它们当新问题重新论证一遍（`Workflow.md` §一）。
3. **第三方对照表**：能力面/取舍与成熟实现（MessagePipe、UniRx、MediatR、VContainer…）并列，特别标出「本仓刻意不做」的那些项——对照的目的不是抄，而是知道**自己在哪、为什么**。
   **对标对象因模块而异**：总线类的对标是同类库（MessagePipe / UniRx），存档类的对标却是平台 SDK（Steam Cloud / PS5 SaveData）与通用做法——后者往往不在可检索的公开资料里。**想不出明确对标物时，如实写「本轮未做」并说明原因**，别用人尽皆知的口号充当对照。
4. **标明实测与推理**（`Workflow.md` §三.2）：哪条是跑出来的、哪条是读出来的，**未能复现的残留要摆到台面上**。
5. **每项的验证方式**：改完怎么证明（改前必红 / 编译复现 / 跑门禁），写进后续的提交计划里。

## 五、结论归档

审计结论按**收件人**分流：使用方要知道的进模块 README，只有维护方要知道的进 `Documentation/Modules/<模块>.md`（不是本文，也不是一次性报告文件）：

| 结论性质 | 落点（按优先级） |
|---|---|
| 使用方需要知道的边界 | 模块 README `## 已知限制`（先例：Update / Settings / Input） |
| 「为什么是 A 而不是 B」，**影响使用方怎么用** | 模块 README `## 设计取舍`（先例：Bootstrap） |
| 接口承诺的边界 | 模块 README `## 接口承诺到哪为止`（先例：Reactive） |
| **已评估未采纳（含理由）** | `Documentation/Modules/<模块>.md` →「已评估未采纳与未决」（逐轮追加，不覆盖） |
| 未决项 | 同上 |

已修的部分不必在 README 记流水——它们在提交信息与 `CHANGELOG` 里；README 要留下的是**下一轮审计需要知道的东西**。

## 六、文档的分工

| 文档 | 写什么 |
|---|---|
| `CLAUDE.md` | **规则**（命名、风格、性能、日志、架构分层、模块边界、文档分层…） |
| `Documentation/Workflow.md` | **流程**（节奏、三条门禁、验证纪律、审计轮） |
| 本文 | **判据与探针**（该看什么、拿什么命令看、看不到什么） |
| `Documentation/Modules/<模块>.md` | **维护记忆**（文件结构、版本沿革、已评估未采纳、逐轮审计记录） |
| `Assets/XFramework/CHANGELOG.md` | **变更流水**（改了什么、为什么、根因与实测证据） |

一处只写一份真相；发现本文与另三份重复的句子，删本文那份、留指针。

## 七、已知边界

- **清单只覆盖「见过的缺陷类」**：它是本仓缺陷史的归纳，**新类型的缺陷它照不到**——每轮审计若发现新类，补进第三节并在提交信息里说明。
- **探针只做诊断，不进门禁**：判定仍靠人。哪些判据将来值得自动化，见下节。
- **审计不替代评审，也不替代门禁**：它产出的是「该改什么」，不是「改对了没有」。
- **不写计数**：条目数、告警数、成员数一律不写进本文——那是会随开发增长的量（见 `CLAUDE.md`「不写固定例数」）。
