# XFramework 候选模块路线图

> **收件人**：框架作者在做模块选型时。**不是**使用文档，也**不是**审计判据。
> 规则在 `CLAUDE.md`，流程与门禁在 `Documentation/Workflow.md`，审计判据在 `Documentation/ModuleAudit.md`，**框架整体体检在 `Documentation/FrameworkReview.md`**——本文不复述它们。
> **与 `FrameworkReview.md` 的分工**：那份文档回答「整个框架缺什么、先做什么」，本文回答「某个候选该不该建、边界画在哪」；**候选模块的边界论证只在本文**，框架评估只留指针。
> **本文件不随 UPM 包发布**：它在仓库根 `Documentation/` 下，第三方在包内看不到它。
> 快照日期：2026-10-11（§三 新增三条、§四 完成一轮复核）。「已有模块」的真相在 `Assets/XFramework/Runtime/` 与 `Documentation/Modules/`，本文不维护副本。

## 一、这份文档怎么用

- 只回答两件事：**该不该建**、**边界画在哪**。门面形状、文件清单、测试与提交拆分属立项后的计划与该模块 README，本文不写。
- **「不该做」也写成结论**（依据 `ModuleAudit.md` §四.2）：已否决项一律带**理由 + 出处**，否则下一轮会把它们当新问题重新论证一遍。
- **模块建成后搬迁**：该模块的条目搬进 `Documentation/Modules/<模块>.md`，本文原地留一行指针。本文只保留**尚未立项**的。
- 状态词只有两个：**待立项**（已确认要做）、**待裁**（常见，但边界未定，先别开工）。

### 2.2 Logger —— ✅ 已建成（2026-10-01）

> **本条已搬迁**。维护向记录在 `Documentation/Modules/Log.md`（含 18 个模块回填的施工图：
> 配方 + 分类映射表），使用方文档在 `Assets/XFramework/Runtime/Log/README.md`——本文只留指针，不再复述。

立项门槛「答得出比 `Debug.unityLogger` + 自定义 `ILogHandler` 多给什么」**三条全部落地**（按分类过滤、
零 GC 调用路径、前缀不靠手抄），评审时另加了一条用户提出的维度：**便于 AI 分析**——结构化 JSONL
落盘 + `logMessageReceivedThreaded` 全量捕获，引擎 / 第三方 / 未捕获异常进同一条时间线。
两个已知坑按预案处理：接口叫 `ILogManager`（`ILogger` 被 UnityEngine 占用）；**回填作为独立批次**，
按模块拆成可独立 review 的提交（施工图已写进模块文档）。

**与立项时的差异**：分类名最后定为「与迁移前的 `[标签]` **逐字**对应」，因此同一模块内历史遗留的多个
标签各是一个分类（`Config` 与 `ConfigManager`、`AssetManager` 与 `YooAssetManager`）——换来的是迁移期间
控制台文本零变化、30+ 处 `LogAssert` 零改动。机械提取全部调用点还纠正了两类误收：
`[AudioManager]` / `[Slot:…]` 不是日志前缀（分别是 GameObject 名与 `SaveMeta.ToString()`），
`[XSerialize]` / `[Reactive]` / `[LanguageAssetLoader]` 则是**异常消息**前缀而非日志标签
——分类表因此定为 31 个，Reactive 与 Serialize 两个模块根本没有日志可回填。

### 2.3 Timer —— ✅ 已建成（2026-10-01）

> **本条已搬迁**。维护向记录在 `Documentation/Modules/Timer.md`，使用方文档在
> `Assets/XFramework/Runtime/Timer/README.md`——本文只留指针，不再复述。

立项时写下的四条理由**全部落地**：可查询的 `Remaining`、零分配的可复用句柄、不漂移的固定间隔、
与 Update 的 Tier 自动升降档联动。**红线照原样执行**：暂停与时间缩放完全转接自 Update 的双时间轴，
模块内没有一行暂停代码、也没有第二条时间口径（`TimerManager` 上刻意没有 `Pause`）。

一轮额外裁定：**不做 `ITimerManager` 接口**。本仓「有接口」的分界线是「是否存在可替换的后端」
（Audio → FMOD、Input → Rewired），Timer 没有——多一个接口只会多出一份必须长期同步的转发契约。
全部理由与代价见模块文档的「已评估未采纳与未决」。

### 2.4 ReactiveList（集合型响应式）—— ✅ 已建成（2026-10-11）

> **本条已搬迁**。使用方文档在 `Assets/XFramework/Runtime/Reactive/README.md`（「集合」节 + 已知限制），
> 维护向记录在 `Documentation/Modules/Reactive.md`（沿革 + 延后项）——本文只留指针，不再复述。

立项时写下的六条边界**全部照原样落地**：只做列表；单一变更流 + `readonly struct` 载荷 + `Reset` 兜底
（索引只在当次通知内有效）；不做 batch 与 Range（批量装载走构造）；回调内改动的三种后果文档化；
零 GC 且 `foreach` 装箱如实写明；`IReactiveList<T> : IReadOnlyList<T>` 且订阅不做立即回调。
**两处与立项时不同**：① 拟有的 `Version` 计数器在实现前砍掉——它是本仓无先例的新契约面，而主线程
同步下「订阅后立即读一次」已是原子的一致点、轮询是比订阅更差的模式（列入 v1.1 候选）；
② `Sort` 定为 `Sort(IComparer<T> comparer = null)`（镜像模块既有的比较器注入措辞，允许零分配静态比较器）。
另一处实现期修正：`foreach` 无论直接用还是经接口**都会**装箱枚举器（原以为只有接口路径会），文档已按实际写。

该轮还顺带修正了 `Documentation/Modules/Reactive.md` 一条**过期未决**（「相等比较器不可注入」——已在
2026-10-02 落地但条目未同步），教训写进该条目自身。

### 2.5 ReactiveDictionary（按键寻址的集合型响应式）—— ✅ 已建成（2026-10-11）

> **本条已搬迁**。使用方文档在 `Assets/XFramework/Runtime/Reactive/README.md`（「集合（`ReactiveDictionary`）」节），
> 维护向记录在 `Documentation/Modules/Reactive.md`（沿革 + 延后项）——本文只留指针，不再复述。

立项时写下的六条边界**全部照原样落地**：只做字典；单流 `readonly struct` 载荷（`Reset` 无哨兵——`Key` 是
`default(TKey)`）；不做 batch / Range；回调内改动按「键稳定、条目会被移除」重写后果；零 GC + `foreach`
装箱如实写明 + 遍历顺序显式不承诺；`IReadOnlyDictionary` 只读视图 + 订阅不立即回调 + 键比较器注入。
**与立项时的差异只有一处**：词表原计划「新建 `ReactiveDictionaryChangeKind`」，实施前改判为**改名共享**
（`ReactiveListChangeKind` → `ReactiveCollectionChangeKind`，39 处 / 6 文件，未发布成本最低）——四个值的
语义完全相同，两套枚举只会各自漂移。实现期另补一条实测：构造决议探针（5 个构造按预期解析；字面量 `null`
→ CS0121，编译级报错非静默）。

**该轮最该记住的一条**：本条**不能**用 §2.4 的论证来理解——`ReactiveList` 的依据是「同一个轮子被每个模块
各写一遍」，而字典逐条核对后**0 处可替换既有设施**（详见条目内的理由），依据是前瞻性使用方场景。这条差异
同时写进了 `Modules/Reactive.md` 的沿革与 CHANGELOG。

### 2.6 场景管理 —— ✅ 已建成（2026-10-13）

> **本条已搬迁**。维护向记录在 `Documentation/Modules/Scene.md`（含四条边界的逐条结论与 S1 / S2 / S3 的
> 落点取舍），使用方文档在 `Assets/XFramework/Runtime/Scene/README.md`——本文只留指针，不再复述。

立项时留下的四条边界**全部照原样落地**：不做场景栈（只给加载原语 + 配对句柄）、不内建加载界面（只给进度
契约）、与 UI 的「切场景框架不做自动检测」共存（本模块不碰 UI）、不给场景间传参通道（只文档化配方与时序，

全是「原语 + 文档」，没有一条变成新 API。

一轮额外裁定：**落点选 S2**——场景原语从 `IAssetManager` 移出，改由能力接口 `IAssetSceneLoader` 承载

所以 Asset 侧必须保留一个能力转发成员（形态同 `ClearPool`）。全部理由见模块文档的「沿革与已否决形状」。

该轮还关掉了立项时未列出的三个**真实缺陷**（失败路径句柄从不 `Release`、取消不中止且此后无人收拾、
按名字回查场景）——记在 `CHANGELOG` 的 `### Fixed`。

**Network 基础层：2026-10-13 裁定「暂不做」，判据可判定**（与下方 App 生命周期同一形态：不进 §四、判据留在这里）。

**为什么不现在做**：① **仓内零消费者**，而且这一处**不可能**由框架内部补上——唯一的网络代码是 `File/MobileFileProvider.cs` 的内部实现（读 StreamingAssets 的机制需要），它不是「想接 HTTP 的地方」；框架自身只该在 `File` 的实现细节里碰网络。② **没有使用方，形状就是猜的**——这一层真正的价值在**编排**（请求队列 / 优先级 / 标签 / 超时 / 主线程回调 / 并发上限），而协议、鉴权、错误码体系全是项目自己的（见上表该行）；`CLAUDE.md` 的「避免臆测」挡的正是这个。**注意这不是「没人要」论据**——那是本仓标注为最弱的一类；这里成立的是「**没有使用方则形状无依据**」，与下面「App 生命周期」同一条判据。

**第三方对照（一手，2026-10-13 读 UGF 源码，非网页转述）**：GameFramework 有同形模块（`GameFramework/WebRequest/`，12 个文件）——`IWebRequestManager` = 请求队列 + 优先级 + 标签 + `Timeout` 属性 + 三个事件 + 并发（由注入的 agent 数量决定），**它同样没有重试**；接口对协议 / 鉴权 / 错误码**零假设**。也就是说：真要做，形状是已知的（照它即可）；缺的不是知识，是使用方。

**升级判据（可判定，不是「想起来就做」）**——任一条成立即从「暂不做」变为「补缺」，届时形状也有依据：

1. **有真实使用方提出该需求**，并给出其协议 / 鉴权形状（主要路径）；
2. `File` 之外的模块出现 HTTP 需求（当前唯一一处在 `MobileFileProvider` 内部，是模块实现细节、不构成可复用面）。

**判据复核**：随框架级评估每轮回填（先例见下方 App 生命周期那条的「判据复核」）。

**与 §四「网络同步框架」是两件事，不要折叠**：§四 否决的是**同步模型**（帧同步 / 状态同步，GamePlay 本体）；本条是**请求 / 重试 / 超时 / 主线程回调**（基础设施）。原句见 §四 的复核记录。

**热更编排：2026-10-13 裁定「不建模块」，真缺口分两处归属**（用户确认）。

**裁定与它推翻的旧判**：原判是「『下载编排』这一半（队列 / 重试 / 续传 / 进度）是纯基础设施，**可进框架**」。本轮逐条核对依赖源码后发现——**这一半已经由 YooAsset 提供**，框架再包一层只会与上游版本耦合地重复一遍编排逻辑。于是结论改为：**不新建模块**，把真缺口按性质分两处归属。

**YooAsset 2.3.18 已经提供的**（2026-10-13 逐条读包内源码核对，**不是网页转述**）：并发控制（`DOWNLOAD_MAX_CONCURRENCY` / `DOWNLOAD_MAX_REQUEST_PER_FRAME`）、看门狗超时（`DOWNLOAD_WATCH_DOG_TIME`）、**断点续传**（`RESUME_DOWNLOAD_MINMUM_SIZE` / `RESUME_DOWNLOAD_RESPONSE_CODES` + `UnityDownloadResumeFileOperation`）、暂停 / 恢复 / 取消（`DownloaderOperation.PauseDownload` / `ResumeDownload` / `CancelDownload`）、进度与逐文件开始回调（`CurrentDownloadCount` / `Bytes`、`DownloadFileBeginCallback`）、**单文件失败重试**（`failedTryAgain` 参数 + `DownloadPackageBundleOperation` 的 `TryAgain` 状态）、CDN 主备站（`IRemoteServices.GetRemoteMainURL` / `GetRemoteFallbackURL`，`_requestCount % 2` 交替）。本仓 `Asset` 已把这些包成 7 个门面成员与一个下载器句柄。

**真缺口（逐条，有证据）**：

1. **预检与下载的版本绑定断了**——这是**缺陷**不是缺口：`PreDownloadContentAsync` 把 operation 丢掉，而 `CreateDownloader` 基于**当前激活清单**，于是「预检之后下载」实际下载的是旧清单的缺口。归 **`Asset`**（证据链与影响面见 `Modules/Asset.md` 的「已评估未采纳与未决」；本轮只订正文档，能力接通另议）。
2. **版本对比**（本地 vs 远端）：无，连版本号语义约定都没有 → **项目侧**。
3. **整体失败重试 / 续跑、下载等待的超时**：无（单文件重试有）→ **项目侧**。
4. **更新决策**（强制门槛 / 公告文案 / 灰度）→ **项目侧**（运营与渠道）。
5. **更新 UI 接线** → **项目侧**。

**第三方对照（一手，2026-10-13 读 UGF）**：UGF 有独立 `Download`（断点续传 + 并发下载器数）与 `WebRequest` 模块，但**没有任何**「更新策略 / 强制更新 / CDN」概念——「更新资源流程」在使用方自己的 Procedure（状态机）里。本仓把 2–5 判给项目侧，与它同向。

**另有一项不进本表**：**App 生命周期**（前后台 / 焦点 / 低内存 / 退出）。2026-10-01 专项盘点后**裁定暂不做**，理由与升级判据记在这里。

**现状几乎不是缺口。** 五个事件里三个已有消费者且工作正常——`Application.quitting` 六处（Update / Lock / Message / Audio / Pool / InstanceTracker，有 `AutoInitTests` 族级守卫）、`Application.lowMemory` 一处（Asset，带开关）、`Application.wantsToQuit` 一处（Settings，带开关）；第四个 `Application.focusChanged` **零消费者**。

> **2026-10-12 订正**：上一段里「六处……有 `AutoInitTests` 族级守卫」当时对 `InstanceTracker` **不成立**——它用的是**静态构造函数 + 匿名 lambda**，而族清单按特性扫描，扫不到静态构造（`Documentation/Modules/Input.md` 当时就指出过这处矛盾，是这句话失实）。本轮已把 `InstanceTracker` 改成具名 `AutoInit`（幂等订阅 + 会话开始清空计数）并登记进族清单，这句话从今天起才成立。原文保留以留痕。唯一的真缺口是 `pause`：Unity 的静态事件里没有它，只能由 MonoBehaviour 接收，而全仓只有一处消费者（`Settings` 自持 80 行宿主，`Runtime/Settings/SettingsPauseNotifier.cs` 的注释正是写着这件事）。使用方入口确实为零——第三方要接前后台只能自己写 MonoBehaviour——但那是十行的轮子。

**为什么不现在做**：唯一真缺口只有 1 个消费者，代价却是一个完整模块（对照刚建成的 Audio：17 文件 / 5 提交 / 136 用例）。更要紧的是，为 1.5 个消费者设计一个公开事件源时，形状（边沿还是电平？`pause` 与 `focus` 是否归一？桌面上什么算「切后台」？订阅顺序？）**每一条都是猜的**，撞 `CLAUDE.md` 的「避免臆测」。

**升级判据（可判定，不是「想起来就做」）**：当**想接 `OnApplicationPause` 的地方达到 2~3 处**（例如 Audio 的 v2 自动暂停落地、或又一个模块被迫自建宿主），**或有真实使用方提出该需求**时，它从「补债」变为「补缺」——届时形状也有依据。

**判据复核（2026-10-11，框架级评估）**：**未触发，维持不做。** 消费者仍是 `Settings` 自持宿主那一处（`Runtime/Settings/SettingsPauseNotifier.cs`），本轮探索未发现新增。

**与「会话级复位」是两件事，不要折叠。** 本文件曾把它归入 §五 的会话级复位一并考虑，那是错的：两者在**验收层面**不成立——

| | 会话级复位 | App 生命周期 |
|---|---|---|
| 本质 | **编辑器开发期**的静态状态跨播放会话存活（关闭域重载才复现） | **运行时**的前后台 / 焦点 / 低内存 / 退出通知 |
| 验收 | 关闭域重载**连跑两遍 PlayMode 全量** | 事件能正确送达订阅者 |

`quitting` 的拆除动作会**暴露**门面没复位这个潜在缺陷，所以两者有交叉；但即使没有 `quitting`，把静态状态带进第二会话本身也是缺陷——**缺的不是「事件」，是「谁在会话开始时把静态状态复位」**。做了 App 生命周期，会话级复位的验收照样通不过。

## 四、已否决（不该做）

| 项 | 理由 | 出处 |

| 状态机 / 行为树 / 实体组件模型 / 时间模型 / 生命周期树 | 任何「使用方必须按某种架构组织游戏逻辑」的设计都不属于本框架 | `CLAUDE.md` → 项目定位 |

| Tween / 缓动 / 动画 | DOTween、PrimeTween 等成熟第三方已覆盖，框架内建只会与它们竞争 | 本轮评估（2026-10-01） |

| 网络同步框架（帧同步 / 状态同步） | GamePlay 本体 | `CLAUDE.md` → 项目定位 |
| **统一框架 Profile / 全局配置文件**（一个文件装 Audio / UI / Log / Save 等模块的值） | ① 与三条既定立场正面冲突：包文档明文承诺「无需额外的框架配置」、架构的**关键设计决策**就是「服务不依赖统一入口」、DI 容器已因「不追求统一」被否；② **引导顺序无解**：Profile 若经 `Config`/`Asset` 加载，就**无法承载 Asset 自身的参数**（包名 / PlayMode / 远端地址——恰恰最需要配的），若自建加载通道则等于新增一条配置来源（时机 / 失败回退 / 加密 / 热更版本化），与「零配置即可用」相斥；③ **共享耦合点**：一个文件装多模块的值，把「模块需要什么」从签名挪进共享类型，破坏「可单独取用」。**真问题另有其解**：「框架约定的名字」清单见包 README（集中登记、零运行时代价）；少数写死的地址要可配，正确形状是各模块自己的 options 字段 / 公开属性（先例 `LogOptions.FileDirectory`、`LocalizationManager.LanguageAssetPath`）。**将来若重开的判据**：只装「编译期决定不了、且与 Asset 引导无关」的值；不替代模块 Options；先回答引导顺序。**判据状态（2026-10-02）**：第三条已满足——引导顺序已契约化（`BootstrapPhases` 常量 + Bootstrap README 的相位表）；但这不构成重开理由，因为第二条判据排除的正是「中心化」这个形状（同轮已把「GameLauncher 作为配置与编排核心」按同样理由否决，见 `Documentation/Modules/Bootstrap.md`） | `CLAUDE.md` → 项目定位；包 README「设计哲学 / 关键设计决策」；本轮评估（2026-10-01） |
| **把模块内部策略接口化**（UI 排序分层 / Update 切片与节拍基 / Message 缓冲「只留最后一条」/ Event 投递顺序 / Timer·Pool·Lock 的静态性） | 这些不是「配置」而是**模块不变量**：换了它，模块的其它保证（遮罩与栈重排、进度聚合与档位估计、缓冲重放语义、订阅快照语义）就不再成立，等于换一个模块。**判据（2026-10-02 全面清点）**：对每个预设问「不想要它时的代价」——一次注入 / 一个 options 字段 = 健康；抄一个实现 = 有边界但要写清；**不可能 = 越界**。该轮据此处理了三处越界出口（Asset 解密服务、Update 自动驱动开关、Input 初始 map 名）与一处死选项，取舍与遗留项见各模块 README 的「已知限制」 | 各模块 README「已知限制」；本轮评估（2026-10-02） |
