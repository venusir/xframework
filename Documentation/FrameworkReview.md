## 一、这份文档怎么用

**它补的是中间那一层。** 此前两种系统性审查都在别的粒度上：

| 文档 | 粒度 | 回答 | 问不出的 |
|---|---|---|---|
| `ModuleAudit.md` | 一次一个模块 | 这个模块内部有没有缺陷 | 「场景管理该不该有」 |
| `Roadmap.md` | 一个候选模块 | 该不该建、边界画在哪 | 「测试覆盖是否失衡」「这个包第三方装不装得上」 |
| **本文** | **整个框架** | **作为一件对外发布的产品，它整体缺什么、该先做什么** | 单个模块的实现细节 |

**本文只做两件事**：① 把框架当成产品体检，列出四个面的缺口与优化项；② 给出**优先级分期**。具体「怎么改」留给每一轮的 Plan Mode，不在本文写施工单（写了必过期）。

**三条纪律**：

- **「不该做」也写成结论**（`ModuleAudit.md` §四.2）。只写「缺什么」的清单会诱导下一轮把已否决的东西重新做一遍。
- **实测与推理分开标**。本文所有**行为性**结论都标了是实测还是读码推理；第三方对照表的来源标了「未一手核对」。
- **时点性 vs 结构性**。上游仓库 HEAD、包版本这类会漂移的结论带日期；结构性结论（某组件缺失、某尺子恒零）可以长期引用。

**读完从哪开始**：要看「下一步做什么」直接跳 §五；要理解某条为什么在清单里，看 §四对应小节。

## 二、现状盘点

**规模**：22 个 Runtime 模块、单一 asmdef `Venusy609.Xframework`。包内约 94,000 行——Runtime 45,595 / Tests 45,591 / Editor 2,185 / Samples 731。9 个月 902 次提交（2026-01-13 → 2026-10-11）。

**测试规模异常地大**：204 个测试文件、152 个 fixture、1963 个 `[Test]`，与 Runtime 行数几乎 1:1。

### 已经领先的地方（对照表的优势列）

不是客套——这些是同类框架普遍没有或做得更浅的：

| 项 | 为什么算领先 |
|---|---|
| **日志系统** | 六档分级 + 分类过滤 + 模板化零分配调用 + 每条一行 JSONL 落盘 + 引擎/第三方/未捕获异常收进同一条时间线。多数框架只包一层 `Debug.Log` |
| **诊断窗口** | 18 个模块面板 + 页签注册契约（`IDiagnosticPanel`）+ 可测的渲染核心。GameFramework 的 Debugger 是同类物，本仓的模块覆盖面更广 |
| **Update 档位时间切片** | `IUpdateable.OnUpdate` 返回 `UpdateTier`，调度器按时长自动升降档。这是 LOD 式更新调度，同行普遍没有 |
| **编排原语** | `Pipeline`（阶段串行/并行/加权进度/失败即停）+ `Bootstrap`（显式登记 + 相位装配 + 逆序清理）。多数框架把启动顺序写死在某个 Manager 里 |
| **模块级文档密度** | 22 个使用方 README + 23 个维护向模块文档 + 18 类审计判据 + 审计技能。这个密度在开源 Unity 框架里罕见 |
| **待办纪律** | 源码里 `TODO/FIXME/HACK` **真标记 0 处**——所有待办与已否决都收敛进文档层，`Roadmap.md` §四 + 各模块「已评估未采纳与未决」 |
| **测试规模** | 45k 行 ≈ Runtime 1:1，含架构守卫（模块边界 / 命名约定 / 自动初始化族清单） |

**这些必须在对照表里显式写出来**——否则本文读起来像一份「到处是坑」的清单，而事实不是。

## 四、缺口与优化项

### 4.1 包内能力缺口

> 探针：`grep -rn "<关键字>" Assets/XFramework/Runtime/` 零命中 + 无目录。下表「零命中」均为此探针结果，属**一手事实**。

#### ★ 场景管理（最大缺口）—— ✅ **2026-10-13 已落地**（`Documentation/Modules/Scene.md`）

**原现状**：只有 `AssetManager.LoadSceneAsync(string, bool additive, Action<float>, CancellationToken)`。**没有**场景栈、场景生命周期、加载界面编排、场景间传参、叠加场景的加载/卸载配对管理；`Runtime/` 下无 `Scene/` 目录。

**原判据**（复核后仍成立）：「一个场景怎么加载、怎么卸载、加载期间显示什么」是**引擎级基础设施**——它不被「不预设 GamePlay」挡住，那条否决的是实体模型 / 生命周期树 / 时间模型。

**四条边界的结论**（逐条回答，完整论证已搬迁至 `Modules/Scene.md` 的「沿革与已否决形状」）：

- **只给加载原语 + 配对句柄，不做场景栈**——「谁在栈顶 / 返回上一场景」= 生命周期树（§六 已否决），与 Update 否决「组」API 同一条推理链；
- **框架不内建加载界面**，只给进度契约与调用方自己的 `await` 窗口；
- **与 UI 的「切场景框架不做自动检测」照原样共存**——场景模块不碰 UI；
- **不给场景间传参通道**，只文档化配方与时序。

**风险没有兑现**：落地的四条边界全是「原语 + 文档」，没有一条变成新 API。该轮另发现并修掉三条**立项清单里没有的**真实缺陷（失败路径句柄从不 `Release`、取消不中止且此后无人收拾、按名字回查场景）。

#### ★ 热更编排 —— ✅ **2026-10-13 已裁定**（§5.2 步骤 8，`Roadmap.md` §三 专段）

**原现状**：`HotUpdate` / `Patch` 零命中。只有 Asset 对 YooAsset 的薄封装 5 个方法（`RequestPackageVersionAsync` / `PreDownloadContentAsync` / `DownloadAssetsAsync` / `CreateDownloader` / `UpdatePackageManifestAsync`）。

**原判**：缺的是决策层（版本对比 → 强制还是可选 → 下载队列与并发 → 断点续传与失败重试 → CDN 切换 → 更新公告与进度 UI 的接线点 → 与 `Bootstrap` 相位的配合）；「更新策略」多半该是「Editor 工具 + 文档」，但「下载编排」这一半（队列/重试/续传/进度）是纯基础设施、**可以进框架**。

**裁定结果（推翻了后半句）**：**不建模块**。2026-10-13 逐条读包内 YooAsset 2.3.18 源码核对后发现——**「下载编排」这一半已经由 YooAsset 提供**：并发控制、看门狗超时、断点续传、暂停/恢复/取消、进度与逐文件回调、**单文件失败重试**、CDN 主备站；本仓 `Asset` 也已把它包成 7 个门面成员 + 一个下载器句柄。框架再包一层只会与上游版本耦合地重复编排逻辑。真缺口两处归属：**接线缺陷**（预检与下载的版本绑定断了）→ `Asset` 的未决；**策略缺口**（版本对比 / 整体重试 / 超时 / 更新决策 / UI 接线）→ **项目侧**。
**顺带核实的三条**：① 该接线缺陷（判据 A1 + 静默失败，已一手坐实到 YooAsset 的 `ActiveManifest`，两处 README + 接口 XML 已订正）；② 四个句柄的 `Status` 透出上游 `EOperationStatus`，与「公开面不出现 YooAsset 类型」的包法不一致——**用户裁定改**，已换框架自有 `AssetOperationStatus`（破坏性）；③ `Modules/Asset.md` 文件结构漏列 1 个源文件、两行描述漂移，已订正。

> 本条**原先不在 `Roadmap.md` 里**——框架级评估首轮新识别；三轮后（2026-10-13）裁定完毕。
