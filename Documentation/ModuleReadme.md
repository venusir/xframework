# 模块 README 结构规范

> **射程**：管 `Assets/XFramework/Runtime/<模块>/README.md`——**随包发布的使用方文档**。
> 别走错门：`Documentation/Modules/README.md`（多个 `s`）管的是 `Documentation/Modules/<模块>.md`（维护向记录），两份不是同一样东西。
> **随包发布的那一份不许引用本文件**：包内一切（README 与源码注释）不得出现 `Documentation/`——第三方装了包打不开它。
> 要指路就写成**自足表述**（结论内联，不给出处路径）。守住这条的是包内的源码扫描守卫。
> 收件人判据（`CLAUDE.md` → 文档分层）：把这段删掉，使用方会不会写错代码或误判行为？会 → 留在 README。

## 一、这份文件解决什么

**解决**：同一件事在 23 份 README 里有几个名字、位置也飘。让读者打开任意一份模块 README，都能按同一条路径找到「它是什么 / 怎么跑起来 / 代码在哪 / 能不能跨线程调 / 哪里会咬人」。

**不解决**：内容的正确性与新鲜度。门禁只查「有没有这一节」，查不了「里面写得对不对」——那是评审与逐轮审计的事（射程详见 §八）。

**普查基线**（2026-10-16，**重整前**，只作动因与对照用、不随重整更新）：23 份共 9196 行；`## 已知限制` 23/23 齐（唯一被守卫锁死的一节），`## 线程契约` 只有 8 家、**11 家一个字没写**；`##` 级标题里只出现一次的有 78 种。**这两组数字的落差本身就是结论：没守卫的约定必然腐烂。**

## 二、一级骨架

**必答**＝每份 README 都要有，答案可以很短（见「最短合法形态」），但不能没有。**按需**＝按判据建，**没有内容的节不建**（判据几乎恒真时按判据走，不要因为「不想写」而跳过）。

| 节 | 类别 | 收件人问题 | 建节判据 / 最短合法形态 | 先例 |
|---|---|---|---|---|
| `## 概述` | 必答 | 这是什么、我该不该用它 | 一段话 + 命名空间。**最短合法形态**：三句话（做什么 / 给谁用 / 与什么容易混淆） | Asset / Config / Settings |
| `## 快速使用` | 必答 | 怎么最快跑起来 | 最小可跑通示例；编号步骤用 `### 1.` `### 2.` 收在下面。**最短合法形态**：一段初始化 + 一次调用的代码块 | UI / Settings / Input |
| `## 模块结构` | 必答 | 我要的类型在哪个文件 | 见 §六。**最短合法形态**：一个 fenced 块，列出模块目录下的全部 `.cs`（`internal` 逐个标注） | File / Save（布局类） |
| `## 行为契约` | 按需 | 我按直觉写会不会错 | **判据**：存在「约定俗成的写法在这里不成立」的行为就必须建（失败返回什么、异常抛不抛、顺序是否保证、重入怎么办）。与 `已知限制` 的分界见 §七 | File / Config / Save / Lock |
| `## 架构设计` | 按需 | 它由哪几块组成、调用链怎么走 | **判据**：模块由 ≥3 个可分辨的块组成 | Asset / UI / Message |
| `## API 参考` | 按需 | 有哪些入口、参数什么意思 | 关键入口 + 契约，**不逐成员抄签名**（签名真相是 XML 注释，抄进 markdown 就是第二本账）。**最短合法形态**：入口一张表 | Asset / Config / Settings / Timer |
| `## 典型场景` | 按需 | 具体某件事怎么做 | **判据**：≥2 条「先做 A 再做 B」的完整配方 | Audio / Lock / Timer / Scene |
| `## 内部机制` | 按需 | 为什么表现是这个样子 | **判据**：不解释运行时模型就说清不某条边界。与 `架构设计` 的分界：**架构 = 静态组成**，**内部机制 = 运行时模型** | Audio / Timer / Scene |
| `## 生命周期与清理` | 按需 | 要不要手动释放、什么时候会被清掉 | **判据**：模块持有可释放资源或跨场景存活 | Audio / Lock / Message / Scene |
| `## 线程契约` | 必答 | 能不能在别的线程调 | **最短合法形态是一句话**，例如「全部 API 仅在主线程调用」。埋在别的节底下的 `###` 不算独立小节，要提升为 `##` | Asset / Audio / Config / File |
| `## 性能代价` | 按需 | 每帧调会不会出事 | **判据**：有实测数字，或能说清明确的分配 / IO 次数 | Log / Pool / Event |
| `## 已知限制` | 必答 | 哪里会咬人 | 条目式。集合类模块可用多条 `### …的已知限制`（现行守卫认可这种形态）。**最短合法形态**：「无已知限制」也要写出来 | 全部 |
| `## 设计取舍` | 按需 | 为什么是 A 而不是 B | **判据**：该取舍**影响使用方怎么写代码**（不影响的不进 README） | Bootstrap / Timer / Scene / Audio |
| `## 接口承诺到哪为止` | 按需 | 哪些行为我别指望 | **判据**：存在「看起来该有、实际刻意没有」的能力，不说明会被反复提问 | Asset / Reactive |
| `## 与相邻模块的关系` | 按需 | 跟别的模块怎么配合 | 一个 `##`；每个对照对象一个 `### 与 <X> 的边界`。对照对象可以是模块、也可以是相邻技术（`UnityEngine.SceneManagement`、C# `event`、Rx） | Audio / Message / Bootstrap |
| `## 设计原则` | 按需 | 它的立场是什么 | 正面陈述。**「本模块不做 X」写在 `设计取舍`，不写这里** | Audio / Lock / Timer |
| `## 依赖` | 按需 | 我要先装什么 | 第三方包 / 其它模块 / Unity 版本要求。无依赖就不建 | Asset / Audio / Config |

**顺序**：按上表从上到下排。**顺序不进门禁**（与维护向那份的既有口径一致）——17 项里只有 5 项人人都有，其余相对顺序各模块的最优解不同，硬性排序只会换来无意义的重排。但 `概述` 一律第一、`依赖` 一律靠尾。

## 三、特性节

一个**自足子系统**的完整用法单独成节，排在 `## 典型场景` 之后，可多个。

**判据**：它有独立入口、独立配置、独立生命周期，删掉它模块其余部分仍成立——**买这个特性的人是从它进来的**，降级成 `###` 就等于把模块主入口藏起来。

节内共用**局部骨架**：

```markdown
## <特性名>（<一句话，可带场景词：NPC / 怪物头顶名字、血条、标记>）

### 快速使用       最小可跑通示例
### 参数 / 配置     该特性独有的配置项与默认值
### 生命周期与回收  谁创建、谁回收、要不要手动
### 已知行为边界    该特性特有的反直觉之处
### 预制体 / 前置条件   有资源约定时才有
```

先例：UI 的 `## HUD 世界空间 UI（…）`、`## Tip 临时提示（…）`、`## 对话框（…）`、`## 弹窗定位（…）`——本规范只是把最大那个模块已经摸索出来的形状写下来。

**特性节不是「找不到槽位就自建一个 `##`」的逃生口**：判据不满足的内容归上方 17 节中最近的那一个。

## 六、文件树的两份分工

`## 模块结构` 是**唯一允许两份并存**的内容，理由只有一个：**发布边界**。`Documentation/` 不随 UPM 包发布，第三方在包内读不到权威副本，而「模块里有哪些文件、哪个文件是我要用的接口」会直接影响他们怎么写代码。

两份的分工固定如下（**2026-10-16 用户裁定：README 也列全、不筛选**——理由是「模块里到底有什么」本身对使用方有价值，而省掉几个文件省不下多少行）：

| | 权威副本 | README 侧 |
|---|---|---|
| 位置 | `Documentation/Modules/<模块>.md` → `## 文件结构` | `Runtime/<模块>/README.md` → `## 模块结构` |
| 收哪些 | 模块目录下的**全部源文件**，另可含测试缝等本目录之外的信息 | **同一批文件，一个不少**；`internal` 的逐个标注出来 |
| 差异只在措辞 | 逐文件**职责详述**（维护者视角：为什么有它、它跟谁耦合） | 同为读代码服务，但从简（使用方视角：哪个文件我要碰、哪个可以忽略） |
| 锚定 | 两边都由**磁盘**锚定——加 / 删 / 改一个文件，两处都要跟 | 同左 |

**格式（README 侧）**：`## 模块结构` 之后**第一个 fenced 块**是唯一被解析的对象，块内每行一个条目，用 `├──` / `└──` / `│` 画树，写**文件名（不含路径）**，行尾可用 `# 说明` 加一句话：

```text
Runtime/Timer/
├── TimerManager.cs        # 静态门面：创建 / 查询 / 清理
├── TimerHandle.cs         # 句柄：剩余量、重开
└── Internal/
    └── TimerScheduler.cs  # 调度实现（使用方不需要直接接触）
```

- **平目录也要写**：没有子目录时按「入口 → 句柄 → 载荷 → 内部件」的顺序平铺即可
- **`internal` 要列、但要标注**（如行尾 `# internal：调度引擎`）——使用方据此知道哪些文件可以忽略。**不要省略它们**：省掉之后「这模块到底有几个文件」就只剩维护向那份有答案，而那份不随包发布
- **机械守卫**（`Tools/check-docs.ps1` 的报告项）校验「README 侧的文件名集合 **==** `Runtime/<模块>/` 下递归的 `.cs` 文件名集合」——**漏收**（磁盘上有、README 没列）与**残影**（README 列了磁盘上没有的）两个方向都抓。**它不比对权威副本**：磁盘才是真相，两份都是派生。**守不住**的仍是对应关系写得对不对（哪个文件在干什么）

## 七、H1 与措辞

**H1 形态**（不进门禁，靠评审）：

```markdown
# <模块> —— <一句话：它是什么 + 给谁用>
```

`<模块>` 逐字用 `Runtime/` 下的目录名。四条理由：与维护向那份的 H1（`# <模块> —— 维护方技术文档`）同形，跨文件跳转不用重新定位；模块名是本仓唯一键（模块索引表、脚本、守卫全部以目录名为准）；`XFramework /` 前缀在包内是冗余；现状 10 家的 H1 根本没有说明句，本来就要补。

**节名措辞**：规范名后可以跟限定词（`快速使用：写一个自己的页签`、`集合（ReactiveList<T>）`），**同义改写不合法**（`快速上手`、`快速入门` 都不算 `快速使用`）。守卫按子串匹配，限定词天然通过。

**`已知限制` 与 `行为契约` 的分界**（最常被搬错的一对）：

- **违约**——承诺过但做不到、有边界条件会翻车 → `已知限制`
- **未承诺**——框架没答应过，但按直觉写就会错 → `行为契约`

## 八、门禁射程

**守卫**：`Tests/Runtime/Architecture/ReadmeSectionTests`（包内，PlayMode 侧）。它守：

- 每个 `Runtime/<模块>/README.md` 存在（模块索引表的链接也按这一条守）
- **五个必答节存在**：`概述` / `快速使用` / `模块结构` / `线程契约` / `已知限制`。只认 `##`（`已知限制` 兼容 `###`），**子串匹配**——限定词与集合级分节天然通过
